# V1 发布、告警与数据库恢复

本次不扩大用户端功能。现有写作交付仍需作者核对研究事实、引用、图表与学校要求，自动审查通过不等于学校认证。数值审查新增完整表格逐列极值上下文，并对明确的“所有变量均为极值”矛盾作有位置的检查；不解析任意统计推论，不改写原始数据、不降低其他交付门槛。

## 两阶段发布

`release.sh --ref <40位提交> --prepare-only` 完成构建、语法检查、全量测试和生产依赖裁剪，产生正常的成功标记及不可变版本，但不备份或切换服务。验收完成后运行同一提交的正常发布，复核标记后，等待当前任务队列清空、快照、再次检查队列，再切换并做健康检查。最后一次检查到重启之间仍有很短的竞态窗口；这不是完整的跨实例排空协议。不要在高峰发布。

低内存服务器可用 `--dependencies /opt/paperknow/dependency-cache/<SHA256>.tar.gz --dependencies-sha256 <SHA256>`。依赖须由相同 Linux x64、Node 二进制、ABI 和 npm 版本从精确锁文件安装；`prepare-dependencies.mjs` 在干净构建目录生成档案和清单。GNU tar 使用 `--hard-dereference`，拒绝硬链接、越界路径、设备、特权位及目录外符号链接。服务器复核哈希、源 package/lock、运行时及档案边界后，由独立构建账号解包，仍执行构建、检查、全部测试和裁剪。清单只用于受控发布缓存，不是第三方签名；缓存和清单必须由 root 安装、不可被普通用户修改。禁止手工创建成功标记。

缓存验证针对 Git 源码锁文件。线上 `npm prune` 后的锁文件可能不同，不得据此绕开验证或修改清单凑过检查。不要复用其他架构、ABI、运行时或不同锁文件的依赖。

## 独立运维邮件

在受保护的 `/etc/paperknow/paperknow.env` 配置 `PK_OPS_ALERT_EMAIL`，复用已有 SMTP 通道；禁止将凭据写进仓库或报告。安装 `paperknow-ops-watch.service/timer`，root 私有状态目录为 `/var/lib/paperknow-ops`（0700），通知状态为 `alerts.json`（0600）。每两分钟巡检，即使 Web 进程停止也能检查本机健康接口、指标新鲜度、磁盘、队列、积分预占、成果存储及已配置的云备份。

连续两次异常才告警，同一问题六小时内不重复提醒；连续两次恢复后发送恢复通知。失败发送至少间隔十分钟重试，保留失败状态并使巡检服务退出失败。通知仅含预定义的服务状态，不含论文、用户身份、任务内容或密钥。`--test-email` 仅由管理员明确授权后执行；SMTP 接受不代表收件人已在收件箱看到邮件。

`systemctl status paperknow-ops-watch.timer` 查看调度，`journalctl -u paperknow-ops-watch.service` 查看安全摘要。该巡检和应用同机，无法在整机断网、关机时自行发信；外部可用性监测仍需独立布置。

## OSS 数据库恢复点

用户原件与生成文件继续仅存原 OSS 桶。本轮新增的是 SQLite 数据库恢复点，不是这些对象的第二份完整副本。`provision-metadata-backup.mjs --apply` 是一次性、明确启用的 root 引导：创建新的私有备份桶、阻止公共访问、默认 SSE-OSS AES256、35 天自动保留规则及专用 RAM API 用户。它不修改生产桶、不授予删除或生产桶读取权限。密钥直接写 `/etc/paperknow/backup.env`（0600），不打印、不进仓库；失败后查看私有引导状态，禁止盲目重试或丢弃刚创建的身份。

专用用户仅可读写该桶 `paperknow-metadata-v1/*` 的对象和读取桶安全属性。每次上传禁止覆盖，读回检查 SSE 标头与完整哈希，最后才发布清单。备份服务每天北京时间 03:35 附近运行，使用 SQLite backup API 合并已提交 WAL；明文临时文件仅在私有 tmpfs 中，不将运行环境密钥上传云端。数据库最大 100 MiB；失败退出并保留失败时间，后续巡检告警。若上传中断，远端可能有不完整对象，不能将其当作成功恢复点。

完成上传后必须再次从 OSS 下载到新建内存目录，检查哈希、数据库完整性、外键及应用表记录数量；通过后写 `backup-status.json`。用 `cloud-metadata-backup.mjs verify <快照UUID>` 可独立重复验证；不覆盖生产数据库、不启动旧任务、不发起支付或 AI。该验证没有模拟全机故障后的登录、支付、全部文件下载；恢复时仍须重新配置或独立恢复应用密钥、域名与支付模型通道。生产配置仍有发布前的 root 私有本机快照，但本机快照不能替代异机恢复。

云端加密由 OSS 托管密钥，不要求用户维护额外恢复密码。备份与生产同属一个云账号，不能称为跨账号灾备，也不能抵御该云账号整体失效或高权限凭据泄漏。不要把数据库恢复验证当作所有 OSS 原件已有独立备份；独立对象副本、生产应用身份最小化迁移及全机恢复演练仍需另行完成和验收。

## 安装与验收

仅从通过检查的发布版本安装这四个 service/timer 文件至 `/etc/systemd/system`；先建立 root 0700 的运维目录，验证服务配置，再启用两个 timer。不改其他项目或系统默认 Node。首次分别手动运行一次巡检与备份服务，核对真实结果后检查下次执行时间。

备份账号必须实测：加密读回、拒绝覆盖、拒绝生产桶访问、拒绝删除目标、拒绝目录外写入、拒绝匿名读取。只用新建合成探针对象，不尝试删除真实文件。探针按同一 35 天生命周期自动清理。
