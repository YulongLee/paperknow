# PaperKnow 首页 SEO 和 GEO 完整设计方案

日期：2026-10-15。适用站点：https://paperknow.cn/ 。状态：已完成代码实现与本地验收；作为本次实现及后续维护依据，线上发布结果以验收记录为准。

PaperKnow 首页已经能展示产品，也具备基本的搜索抓取条件；接下来的重点是让每项服务拥有可独立理解的公开页面，让官网的产品事实保持准确一致，并能观察搜索访问是否带来真实使用。首页保留当前视觉风格、写作主题、8 项功能导航与卡片轮播，围绕这些基础补齐内容和技术体系。

本方案将中文搜索用户作为第一批受众，覆盖百度、Bing、Google 的发现与索引，以及采用网页检索的 AI 搜索场景。各平台能否收录和引用，需要实际观测，不能通过标签数量或一个 GEO 分数确认。

## 1 现状判断与目标

### 已确认的基础

- HTTPS 首页返回 200；有中文 title、description、一个主要 H1、语言和移动视口设置。
- 8 项能力说明与 4 条常见问题的正文位于初始 HTML 中。轮播只控制展示，不需要等待点击才能从服务器获取文本。
- HTTP 与 www 已永久跳转到 HTTPS 根域；不存在路径返回真实 404。
- 线上已经启用 gzip，压缩不是本次确认的缺口；后续应核查响应变体与缓存配套。
- 最新轮播移除了用户不需要的进度条、页码、暂停按钮和底部说明，继续保留自动展示、标签切换与交互暂停。

### 需要补齐的内容

| 缺口 | 当前证据 | 本次设计的处理 |
|---|---|---|
| 功能无法分别形成公开服务文档 | 8 个入口均为 `/workspace.html#category/...`，工作台初始 HTML 为空挂载容器 | 建立 8 个公开服务介绍页，与现有操作入口互相衔接 |
| 基础抓取配置不完整 | robots、sitemap 返回 404；首页无 canonical | 规范网址、页面索引分区、站点地图和明确的抓取策略 |
| 品牌和软件信息缺少统一表达 | 首页无 JSON-LD、Open Graph；关于产品只有弹窗 | 公开产品档案、真实结构化信息和分享摘要 |
| 缺少可核实的使用证据 | 首页大部分是已标注的界面与结构示意 | 增加自制材料的可复现教程和实际输出样本 |
| 部分内容矛盾或缺少依据 | 帮助页仍称在线账户未接入；“千万”文案无可见统计依据 | 统一产品事实与发布状态，核实宣传口径 |

当前公开能力接口显示：账户已开放；在线 AI、支付、学术检索未开放；在线上传上限为 2 MiB。该上限只代表本次核对到的在线接口，不能直接套用于所有本地工具。

### 商业目标与衡量方式

1. 搜索用户进入与需求匹配的页面，能判断工具是否适用。
2. 理解服务范围后进入正确流程，完成一次实际任务。
3. 有持续使用需求的用户注册账户，保存项目与成果。
4. 支付正式开放后，再衡量自然搜索用户的付费转化。

当前不设置凭空的流量、排名或 AI 引用率目标。先建立基线，再用连续数周的数据决定重点页面和内容投入。

### 首页问答建议稿

**PaperKnow 可以帮助完成哪些论文工作？**

PaperKnow 将论文大纲与章节编辑、文献资料、材料比对、格式整理、PPT 创作和科研图表放在一个工作台中。部分能力需要在线服务配置，具体使用范围以各工具中的状态说明为准。

**AI 写作能否直接生成可提交的论文？**

当前可使用大纲、内容编辑和草稿管理等能力；在线 AI 生成以服务实际开放状态为准。研究数据、论证、引用和最终内容需要由使用者核实并完善。

**免费查重可以替代学校指定的检测吗？**

当前材料比对用于检查论文与用户导入正文之间的相似片段，不是全网正式查重，不能替代学校要求的检测结果。

**是否需要下载客户端？**

网页端目前可直接使用。macOS 与 Windows 客户端尚未发布，正式上线后再提供安装包、版本和下载说明。

**文件、草稿和项目保存在哪里？**

本地体验的数据保存在当前浏览器；账户中的在线项目和文件由账户服务保存。两种空间分别管理，需要及时备份。本地体验数据不会因为登录就自动成为在线项目。

**PPT 和论文内容可以导出吗？**

不同工具支持不同成果格式，例如可编辑 PPTX、排版后的 DOCX 副本、图形与数据等。论文正文、大纲及其他成果的开放条件，以相应工具的实际导出状态为准。

**当前可以付费购买方案吗？**

付费购买目前尚未开放。价格、计费方式、权益和交付规则应在正式发布后统一展示。

这些问答用于直接解决用户问题，不承诺 FAQ 富结果，也不新增商业站不适用的 FAQPage 或 HowTo 富结果标记。

## 5 技术与索引规则

### 公开页面与操作页面分区

| 页面类型 | 索引设计 | 安全与实现 |
|---|---|---|
| 首页、有效功能页、完整指南 | 可抓取与索引，自身 canonical，进入 sitemap | 初始 HTML 含正文；正常链接可发现 |
| About、帮助、状态、隐私、协议、联系 | 公开可读；有实质内容时可索引 | 不公开管理员账户、私人联系方式或内部配置 |
| 工作台、登录、项目、任务、成果操作 | 不作为公开搜索落地页，使用 noindex | noindex 不是权限控制；私人数据继续依靠认证 |
| 管理后台、API、原件与私人下载 | 不进入 sitemap | 保留服务端授权、有效期等实际权限规则；不公开用户上传文本 |
| 品牌预览、测试和无用演示 | noindex，取消公共导航入口 | 可移除时另行清理 |
| 不存在页面 | 真实 404 | 不返回首页 200；对用户提供可返回的入口 |

### 路径与规范网址

- 主站固定为 `https://paperknow.cn/`，HTTP 与 www 保留现有单跳永久跳转。
- 首页 `/index.html` 永久跳转到 `/`；公开介绍页统一小写和尾斜杠，别名永久跳转到唯一形式。
- 每个公开页设置完整 HTTPS canonical；分享 URL、JSON-LD URL、sitemap URL 与它一致。
- 营销参数采用无参数 canonical，但不能全站盲目删除查询参数：登录回跳、合法功能参数和旧工具入口必须保留原有语义。
- 旧 `?tool=`、草稿与历史链接继续按原流程处理，不强行跳到 SEO 介绍页。
- 不给不存在的英语版本加 hreflang；有真实对应内容后才设计多语言映射。

### 适合当前项目的实现

当前是原生 HTML/CSS/JS 与 Node 服务，无需仅为 SEO 更换整个框架。公开页可以按内容数据生成静态 HTML，统一复用导航、页脚和元信息组件。

服务端需要明确将 `/features/.../`、`/guides/.../` 等设计路径映射到实际文件，正确处理目录刷新；不能只生成链接却没有对应路由。当前 MIME 映射还需补充 XML、TXT 以及分享图片等实际使用格式。XML sitemap 与 robots 文本应分别返回准确 Content-Type。

### robots 与 sitemap

- robots 明确允许公开内容抓取，声明 sitemap 地址；避免误封 CSS、JS 和必要媒体。
- 对不希望公开的路径制定规则，但不能依赖 robots 隐藏私人文件；需要爬虫读取 noindex 的页面也不能直接一并屏蔽后误认为已经移除索引。
- sitemap 只列实际发布、可索引、返回 200 的规范 URL，不含 hash、登录页、项目、参数副本和错误页。
- `lastmod` 使用实际内容修改时间，不每天自动改日期；生成过程校验 URL 唯一性和存在性。
- 首次发布和后续新增页面后，通过已经验证的站长平台检查提交状态。

### 性能与动画

保持轮播的固定高度、交互暂停与减少动态效果设置；所有卡片正文继续在 HTML 中提供，自动展示不创建新 URL。

对现有多份样式进行使用情况核查；公共静态资源采用内容版本或明确的更新策略后再设置缓存。公共 HTML 可以采用重新验证，带内容指纹的资源才适合长期 immutable；未指纹 CSS/JS 采用短缓存或重新验证。登录、账户与私人 API 不采用公共长缓存，不能将当前统一 no-store 简单改成全站缓存。gzip 已有，需核查 `Vary: Accept-Encoding` 等响应变体策略；不能仅凭样式数量认定性能失败。

性能验收目标为真实访问第 75 百分位：LCP ≤2.5 秒、INP ≤200 毫秒、CLS ≤0.1，并区分移动与桌面。当前未取得有效实测，不能声称已通过。Lighthouse 的实验室分数也不能代替真实交互的 INP。[Web Vitals 官方说明](https://web.dev/articles/vitals)

## 7 GEO 的内容与引用设计

### 统一官方产品事实

建立同一份可维护的事实清单，供首页、功能页、帮助、状态页和结构化信息引用：

- 产品名称、正式域名、服务对象、网页端与客户端状态。
- 每项功能当前可用、需配置、待开放的能力及生效日期。
- 输入格式、上传限制、输出格式和导出条件。
- 本地体验与在线账户的数据保存差别。
- 当前收费开放状态与正式联系渠道。

状态页应有更新时间。若实际能力改变，发布过程同时更新相关 HTML 与说明；不能让旧帮助继续声称账户未接入。公开页面不为获取状态而泄露密钥、内部接口地址或后台设置。

### 让内容能够直接回答问题

先明确回答，再解释条件、步骤和依据。以本地材料比对为例：

> PaperKnow 当前的材料比对只检查论文与用户导入正文之间的相似片段。它不查询全网学术数据库，不能替代学校指定平台的正式检测；结果适合用于核对引用和来源。

这类答案可以独立理解，也能准确表达限制。无需为了 AI 强行规定每段字数或堆放“最佳工具”等自我推荐语。

### 原创证据的发布标准

每个实际案例包括：材料来源与使用权限 → 样本或关键输入 → 工具与版本 → 实际操作 → 输出样本 → 人工复核结果 → 未覆盖范围 → 更新时间。自制材料可以公开，用户论文和私人数据不作为默认营销案例。

使用界面示意时继续注明示意；使用真实处理结果时给出复现条件，不把界面示意改成“实测成功”。对外比较竞品前重新核实其当前资料，不复用竞争对手品牌图或检测报告冒充 PaperKnow 结果。

### 爬虫与平台

Google 的生成式搜索沿用 SEO 基础，没有额外必需的 GEO 文件或特殊标记；其官方指南说明 `llms.txt` 不影响 Google Search 排名。可以为其他系统需要维护辅助导航文件，但应在真实公开页面发布后再写入有效链接。[Google 官方指南](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide)

OpenAI 的 OAI-SearchBot 用于搜索，GPTBot 用于训练，可分别管理。搜索可发现性不要求必须开放训练抓取；robots 允许也不保证防火墙一定放行，需验证官方爬虫请求与日志。[OpenAI 爬虫说明](https://developers.openai.com/api/docs/bots)

当前先维持公开内容对搜索抓取可达，训练抓取政策作为独立选择。新增特定爬虫分组时，检查它是否覆盖而非继承通用组的路径规则，避免只写 Allow 而漏掉原有限制；Google-Extended 也不能当作 Google 搜索是否抓取的总开关。

百度与其他国内平台以各自公开支持的站长工具、实际访问与引用为观察依据。不给未经核实的平台写虚构 User-Agent，也不承诺某一模型必然推荐 PaperKnow。
